## Concrete port hazards

1. **26.1.2 has a distinct build contract.** Apply `net.fabricmc.fabric-loom`, remove `mappings(...)`, use `implementation`/`compileOnly`/`api` instead of corresponding `mod*` configurations, and package `jar` instead of `remapJar`. Retain remapping for every older Fabric module. Old Minecraft-linked dependencies cannot be reused without compatible builds; Minecraft-free core libraries are a different case. Tickwatch already uses Mojang mappings, so it needs no Yarn migration first. [Exact-version Fabric porting guide](https://docs.fabricmc.net/26.1.2/develop/porting/), [plugin IDs](https://docs.fabricmc.net/26.1.2/develop/loom/).
2. **1.21.8 must not inherit the 1.21.11 permission implementation.** The newer vanilla permission system replaces integer command levels with `PermissionCheck` and `PermissionSet`. Keep the older integer predicate in 1.21.8; keep the existing typed implementation in 1.21.11 and verify it on 26.1.2. The official primer assigns the `ResourceLocation` → `Identifier` rename to 1.21.11; some local historical tables describe a different boundary. [NeoForge vanilla 1.21.11 migration primer](https://github.com/neoforged/.github/blob/main/primers/1.21.11/index.md).
3. **Fabric API also renames symbols independently of mappings.** In 26.1, world events become level events (for example `ServerEntityWorldChangeEvents` → `ServerEntityLevelChangeEvents`, `END_WORLD_TICK` → `END_LEVEL_TICK`). Tickwatch currently uses server ticks, not world ticks. Its `ServerLivingEntityEvents.AFTER_DEATH` and two-argument `(LivingEntity, DamageSource)` callback are present in API `0.155.3+26.1.2` (checked with `javap` on its `fabric-entity-events-v1:5.0.2+e2bdee784c` jar). Check every actual import instead of globally replacing names. [Fabric API rename list](https://docs.fabricmc.net/26.1.2/develop/porting/fabric-api).
4. **Exact 26.1.2 vanilla inspection:** cached Mojang `minecraft-common.jar` retains `Player.getGameProfile()`, entity UUID/rotation getters, `DamageSource.getEntity()`, `MinecraftServer.getWorldPath(LevelResource)`, supplier-based `CommandSourceStack.sendSuccess`, and `Commands.LEVEL_*` typed checks. This supports reusing Tickwatch's narrow 1.21.11 adapter design, but compilation and runtime remain the proof. [Vanilla artifact metadata](https://piston-meta.mojang.com/v1/packages/0bbfbdb8272531060afbba5c671fe4ed3dd6f72f/26.1.2.json), [26.1 vanilla migration primer](https://github.com/neoforged/.github/blob/main/primers/26.1/index.md).
5. **Broader mods have additional 1.21.8 changes.** Fabric's 1.21.6–1.21.8 notes document removed command-v1 modules, rendering API changes and new NBT views. These are migration checks for mods that use those systems, not reasons to change Tickwatch's JSON storage. [Fabric 1.21.8 changes](https://fabricmc.net/2025/06/15/1216.html).

All remaining Tickwatch Fabric callback signatures were checked with `javap` on the exact API 0.155.3 modules: `CommandRegistrationCallback.EVENT` takes dispatcher, `CommandBuildContext`, `Commands.CommandSelection`; `SERVER_STARTING`, `SERVER_STOPPING` and `END_SERVER_TICK` each take `MinecraftServer`; `JOIN` takes `ServerGamePacketListenerImpl`, `PacketSender`, `MinecraftServer`; `DISCONNECT` takes handler and server. Existing lambda arities remain valid. Artifacts: [command API 3.0.5](https://maven.fabricmc.net/net/fabricmc/fabric-api/fabric-command-api-v2/3.0.5+e2bdee784c/fabric-command-api-v2-3.0.5+e2bdee784c.jar), [lifecycle 4.1.1](https://maven.fabricmc.net/net/fabricmc/fabric-api/fabric-lifecycle-events-v1/4.1.1+df84eb3d4c/fabric-lifecycle-events-v1-4.1.1+df84eb3d4c.jar), [networking 6.3.2](https://maven.fabricmc.net/net/fabricmc/fabric-api/fabric-networking-api-v1/6.3.2+a217cccf4c/fabric-networking-api-v1-6.3.2+a217cccf4c.jar).

## Packaging, runtime and release checks

Inspect every final jar for expanded metadata, its exact Minecraft/loader ranges, the intended bytecode level, bundled `com/fiw` core classes and required language providers. Tickwatch explicitly requires Fabric Language Kotlin or Kotlin for Forge: preserve these runtime requirements unless deliberately changing the architecture. Its existing NeoForge/Forge jars merge only Minecraft-free core output, not Kotlin stdlib.

Run core tests, build every declared target, then boot **production jars** with matching loader/API/Kotlin dependencies in disposable worlds; require `Done`, exercise real console commands, stop cleanly, and restart to check persistence. A successful dev `runServer` can miss jar packaging failures; a dev classpath failure also need not mean the production jar is broken. Fabric documents [production run tasks](https://docs.fabricmc.net/26.1.2/develop/loom/production-run-tasks), but that page retains remapping wording from older versions: follow the exact 26.1.2 porting guide for output naming. NeoForge documents installing the built jar into `mods/` in [its testing guide](https://docs.neoforged.net/docs/1.21.8/gettingstarted/).

Local reusable conventions were read from the Tools/Bosses/AntiCheat Markdown. Their latest session notes distinguish real server boots from player gameplay; some older notes describe sandbox failures later superseded by successful runs. Tools records a NeoForge JPMS conflict from merging Kotlin stdlib with `zipTree`; its `jarJar` solution is specific to that mod's self-contained runtime policy. Local run isolation differs: Loom uses `projectDir` + `internalRunDir`, ModDevGradle uses `gameDirectory`, ForgeGradle uses its run `workingDirectory`. Do not let smoke tests open existing worlds.

Tickwatch's current release workflow auto-tags and publishes a new root `mod_version` on a push to `main`; `.github/scripts/targets.sh` controls the release jars and Modrinth target metadata. Adding modules requires updating settings, CI JDKs, this target list, README/store requirements and artifact collection together. Retain the existing channel choice and public API; building a port does not authorize publishing it.
